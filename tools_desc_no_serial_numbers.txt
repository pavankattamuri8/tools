
Action Groups – Azure Notifications
 What is it?
Azure Action Groups is a feature in Microsoft Azure Monitor that defines a collection of notification preferences and automated actions to be triggered when an alert fires. Think of it as a "response team contact list  automation rulebook" — when something goes wrong in your Azure environment, Action Groups decide who gets notified and what automated action runs.

 Where It Fits in DevOps
DevOps PhaseRole of Action GroupsMonitorTriggers when Azure Monitor detects anomalies or threshold breachesAlertingSends alerts via Email, SMS, Push, VoiceIncident ResponseAuto-triggers runbooks, webhooks, or Logic AppsOperations (AIOps)Integrates with ITSM tools like ServiceNow, PagerDuty

 Key Notification Channels Supported

 Email / SMS / Voice call
 Azure Mobile App Push Notification
 Webhook (call any external HTTP endpoint)
 Azure Automation Runbook (auto-remediation)
 Azure Logic Apps (workflow automation)
 ITSM Connector (ServiceNow, Cherwell)
 Azure Functions (serverless action)


 Real-Time Use Case

Scenario: Production Server CPU Spike Alert


Your AKS (Azure Kubernetes Service) cluster's CPU usage crosses 90% threshold.
Azure Monitor detects the breach and fires an alert.
The alert is linked to an Action Group which:

 Sends an email to the DevOps team
 Sends an SMS to the on-call engineer
 Calls a Webhook to notify a Slack / Teams channel
 Triggers an Automation Runbook to automatically scale out the node pool


The on-call engineer gets notified within seconds, and the system auto-heals before users are impacted.


 Simple One-Line Summary

Action Groups in Azure  "When an alert fires, notify the right people through the right channels and optionally trigger automated fixes — all in one configured group."




AKS — Azure Kubernetes Service
 What is it?
AKS (Azure Kubernetes Service) is a managed Kubernetes container orchestration service provided by Microsoft Azure. It takes away the complexity of setting up and managing Kubernetes clusters — Azure handles the control plane (master nodes) for you, and you just manage your worker nodes and applications. It's the go-to platform for deploying, scaling, and managing containerized applications on Azure.

 Where It Fits in DevOps
DevOps PhaseRole of AKSBuildPulls container images from Azure Container Registry (ACR)DeployDeploys microservices as pods/containers into clustersScaleAuto-scales pods (HPA) and nodes (Cluster Autoscaler)MonitorIntegrates with Azure Monitor & Prometheus for observabilityOperateRolling updates, self-healing, zero-downtime deployments

 Key Features

 Managed Kubernetes control plane (no master node management)
 Auto-scaling (Horizontal Pod Autoscaler  Cluster Autoscaler)
 Azure Active Directory (AAD) integration for RBAC
 Native integration with ACR (Azure Container Registry)
 Built-in Load Balancing & Ingress support
 CI/CD integration with Azure DevOps & GitHub Actions


 Real-Time Use Case

Scenario: E-Commerce Application Deployment


A team builds a microservices-based e-commerce app (cart, payment, product, user services).
Each service is containerized using Docker and pushed to ACR.
AKS deploys all microservices as separate pods in the cluster.
During a sale event, traffic spikes — AKS auto-scales pods from 3  20 replicas automatically.
A bad deployment is pushed — AKS auto-rolls back to the previous stable version with zero downtime.
Azure Monitor  Action Groups alert the team if any pod crashes.


 Simple One-Line Summary

AKS  "Azure's fully managed Kubernetes platform to deploy, scale, and operate containerized applications without worrying about cluster infrastructure."

ALB — Azure Load Balancer
 What is it?
ALB (Azure Load Balancer) is a high-performance, Layer 4 (TCP/UDP) traffic distribution service in Azure. It distributes incoming network traffic across multiple backend servers or VMs to ensure no single server is overwhelmed, providing high availability and fault tolerance. It works at the transport layer and is ideal for handling millions of requests per second.

 Where It Fits in DevOps
DevOps PhaseRole of ALBDeploySits in front of VMs/AKS nodes to distribute trafficOperateEnsures high availability by rerouting traffic from unhealthy nodesScaleBalances load as new instances are added during auto-scalingMonitorHealth probes continuously check backend server statusSecurityWorks with NSGs (Network Security Groups) to filter traffic

 Key Features

 Layer 4 Load Balancing (TCP/UDP)
 Health Probes — auto-detects and removes unhealthy backends
 Public & Internal Load Balancer options
 Supports millions of flows with ultra-low latency
 Works seamlessly with VM Scale Sets & AKS
 Outbound NAT for backend VMs to access the internet


 Real-Time Use Case

Scenario: Banking Application with High Availability


A bank runs its core banking portal on 3 Azure VMs behind an ALB.
ALB receives millions of user login/transaction requests and evenly distributes them across all 3 VMs.
One VM suddenly crashes due to a hardware fault.
ALB's health probe detects the failure within seconds and stops sending traffic to the crashed VM.
All traffic is seamlessly routed to the remaining 2 healthy VMs — users experience zero downtime.
When the VM recovers, ALB automatically adds it back to the pool.


 Simple One-Line Summary

ALB  "Azure's Layer 4 traffic distributor that ensures your applications stay fast, available, and fault-tolerant by smartly routing requests across healthy backend servers."

 Real-Time Use Case

 UFW — Security – Firewall
 What is it?
UFW (Uncomplicated Firewall) is a user-friendly frontend for iptables — Linux's built-in packet filtering firewall — designed to make firewall management on Ubuntu/Debian Linux servers simpler. In DevOps, UFW is used to control inbound and outbound network traffic on Linux servers — allowing only necessary ports and blocking everything else, following the principle of least privilege for network access.

 Where It Fits in DevOps

 Common UFW Commands
bashufw enable                    # Enable firewall
ufw allow 22/tcp              # Allow SSH
ufw allow 80/tcp              # Allow HTTP
ufw allow 443/tcp             # Allow HTTPS
ufw deny 3306                 # Block MySQL from outside
ufw allow from 10.0.0.0/8    # Allow internal network
ufw status verbose            # View current rules

 Real-Time Use Case

A new Ubuntu EC2 instance is provisioned via Ansible. The playbook runs UFW commands to: allow SSH (port 22) only from the VPN IP range, allow HTTP (80) and HTTPS (443) from anywhere, deny all other inbound traffic. A security audit finds a dev server with MySQL port 3306 open to the internet — UFW rule ufw deny 3306 closes it immediately. All firewall configs are stored in Ansible playbooks and version-controlled in Git.
